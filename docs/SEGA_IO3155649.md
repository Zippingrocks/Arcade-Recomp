# Sega 315-5649 serial I/O: independent original HOTD1 research

**Status: PARTIAL, SYNTHETIC-TESTED. NOT arcade-hardware verified or a complete I/O chip.**

## Original arcade target and evidence

The primary artifact is the verified **`hotdo` original Sega Model 2C arcade revision**, not `hotd` Revision A and not the Windows/Saturn adaptations. The user's private ROM set was previously confirmed against 29 published chip fingerprints. Proprietary program and asset bytes are **not** checked into this repo.

There are two independent kinds of evidence here:

1. **ROM-observed commands.** Local static i960 disassembly of the authentic original `hotdo` startup addresses, recorded below. This establishes what the game *requests*, not how physical I/O devices responded.
2. **Published hardware register maps.** Model 2C's memory map associates `0x01c00000..0x01c0001f` with a Sega 315-5649 device on 8-bit lanes in a 32-bit i960 word. Historical service-document annotations and MAME's I/O inventory name its register functions. These descriptions are *references*, not software to copy.

### Original startup path

| Original HOTD1 i960 address | Verified static observation | Why it matters |
| --- | --- | --- |
| `0x0000068c` | `CALL` to `0x000a3750` | Enters arcade I/O setup |
| `0x000a3750` | Load base `0x01c00000` | Addresses Sega I/O aperture |
| `0x000a375c` | Byte write to `0x01c00014` of `0xff` | Channel 2 serial TX command |
| `0x000a3764` | Byte write to `0x01c00012` of `0x01` | Channel 1 serial TX command |
| `0x000a3768` | `CALL` to `0x000a3720` | Polls for both RX buffers |
| `0x000a376c` | Byte read from `0x01c00016` | Channel 1 RX byte |
| `0x000a3770` | Byte read from `0x01c00018` | Channel 2 RX byte |

This is a *static* reconstruction from the original program's instructions. **The revised native implementation has not yet been shown executing this specific original-ROM sequence with correct physical device responses.**

### Verified waiting loop at `0x000a3720`

At `0x000a3720`, the program loads the I/O base, prepares the mask `0x0c`, reads the status byte at offset `0x1a`, masks that byte with `0x0c` and loops until the masked result equals `0x0c`. It then returns to the caller, which reads the two serial RX bytes. The register inventory labels bits 2 and 3 of the serial status as *RX1/RX2 buffer full*.

**Important:** `0x0c` is the status condition the game *waits for*. It is **not** a valid justification for making every status read return `0x0c`. Some existing emulation code uses that shortcut. ArcadeRecomp deliberately does not.

## CPU address / 315-5649 register mapping

The Model 2C bus maps the 8-bit device to even CPU-byte addresses, consistent with a 32-bit I/O lane mask of `0x00ff00ff`. We currently support:

| i960 physical address | Chip register | Meaning | ArcadeRecomp behavior |
| --- | --- | --- | --- |
| `0x01c00012` | `0x09` | RS422 TX1 | Records transmitted byte and notifies an optional output consumer |
| `0x01c00014` | `0x0a` | RS422 TX2 | Records transmitted byte; input-handler/multiplexer integration is future work |
| `0x01c00016` | `0x0b` | RS422 RX1 | Requires an explicit external provider; otherwise throws |
| `0x01c00018` | `0x0c` | RS422 RX2 | Requires an explicit external provider; otherwise throws |
| `0x01c0001a` | `0x0d` | RS422 status | Requires an explicit external **status** provider; never fabricates ready bits |

Other registers include digital I/O, direction settings, serial mode and an analog multiplexer. Their behavior is **not implemented**. Even-byte addresses are selected only under the documented device layout; odd or wide accesses are refused pending stronger evidence.

## Our independent implementation

- `runtime/sega3155649_serial.hpp` is a dedicated, original serial interface, with an explicit event stream and two independent channel states.
- `runtime/model2c_bus.hpp` provides opt-in serial TX support; the **default remains fully strict**, rejecting even documented serial writes until explicitly enabled.
- No missing serial receive byte or status is replaced by a guessed constant. An injected input/status provider is for hardware integration or a **clearly labeled synthetic fixture**.
- Native translated byte loads/stores use dedicated 8-bit bus callbacks, not 32-bit RAM substitution.
- `tools/hotd1_strict_boot_probe.cpp` can opt into known serial writes using `--serial-tx`. It logs transmitted bytes and stops when status or another unimplemented hardware device is needed.
- `tests/test_sega3155649_serial.py`, `tests/test_hotd1_serial_poll.py`, and `tests/test_hotd1_serial_probe.py` compile and execute **artificial** instructions to check mappings, ordering, explicit status injection, and strict refusal.

## What remains unverified

- Original Model 2C RS422 transmit/receive timing and buffer state transitions
- True status reset values, transmit full conditions and receive-ready timing
- Lightgun mux electrical protocol, calibrated X/Y, triggers and offscreen reads
- Complete I/O port mapping, direction and EEPROM interactions
- A native full-original-ROM trace through this routine with a measured cabinet-grounded response
- Graphics coprocessor, sound, video, timers and interrupt behavior

Until those are implemented and tested, **Model 2C is not complete**. There must be no shortcut analogous to emulator fixed-0x0c serial status that makes the game *seem* to boot.

## Additional primary source leads reviewed October 2026

These are first-hand reports by their authors, **not captures made or independently
reproduced by ArcadeRecomp**. No reported frames, timing values or responses have
been imported into a runtime device, replay fixture or authenticated HOTD trace.

### Original Daytona I/O measurements are not HOTD gun-board evidence

BigPanik's [original project description, May 2007](https://www.gamoover.net/Forums/index.php?msg=155517)
identifies Daytona USA's separate I/O board as the target. His
[November 13, 2009 measurement report](https://www.gamoover.net/Forums/index.php?msg=291805)
describes probing its transmit/receive signals with a logic analyzer, idle-high
levels and approximately 500 ns bit periods. A
[November 15 follow-up](https://www.gamoover.net/Forums/index.php?msg=292161)
describes four cyclic frames and an approximately 700 ns response offset; the
posts link board photographs, waveform images and a traced schematic.

This is an independent lead for examining older Sega serial framing, not proof
that the Model 2C 315-5649 or 837-12079 uses the same transaction semantics.
Neither report supplies HOTD's startup status register, its two RX values, or a
CPU-access-correlated gun-board capture. In particular, do not convert the
author's provisional framing interpretation into a verified UART format.

### Working gun-board conversions establish compatibility, not protocol

Two contemporary reports document physical Lost World cabinet conversions:

- [Lost World conversion discussion, page 2](https://forums.arcade-museum.com/threads/lost-world-happ-gun-conversion.327500/page-2):
  post 29 (August 18, 2015) reports a completed conversion; post 35 (November 13,
  2015) identifies the HOTD/Virtua Cop 2 gun-sensor board as **837-12079** and the
  Model 3 serial connector as CN10.
- [Tested ATX and Happ 45 conversion wiring](https://forums.arcade-museum.com/threads/lost-world-sega-model-3-power-supply-to-atx-and-happ-45-gun-conversion.351380/):
  posts 12 and 13 (August 14, 2015) document the author's corrected serial harness
  and working gun connections. The correction is a reason to verify connector
  orientation on real hardware, not to infer a byte protocol from wire labels.

These reports broaden the possible physical reference setups. They do not
contain a gun-board serial capture, reset/status semantics or an independently
decoded response to HOTD's startup commands.

### Public 315-5649 silicon measurements narrow the transport contract

The Model 2B homebrew [m2-sdk RS-422 transport at immutable commit
`f952efb`](https://github.com/biggestsonicfan/m2-sdk/blob/f952efb0bf7445f2d2cee1c9a6cca93af4194106/src/m2_rs422.h)
reports first-hand logic-analyzer and live-FTDI measurements of the same
315-5649 part.  Its author reports idle-high 8-N-1, LSB-first signaling at
2.000 Mbaud, observes both TX registers serializing, and waits for status bits
2 and 3 before draining both receive registers.  The header also records an
important negative result: a deployed board can idle with status bit 6 clear,
so that bit is not a reliable hardware-versus-emulator discriminator.

The same commit's detailed [protocol
note](https://github.com/biggestsonicfan/m2-sdk/blob/f952efb0bf7445f2d2cee1c9a6cca93af4194106/docs/rs422-serial-protocol.md)
draws a narrower evidence boundary: it labels TX byte accuracy and outbound
wire format as live-confirmed, while listing reliable bidirectional RX wiring
and the per-byte lockstep acknowledgement as work still to do.  Consequently,
the SDK's firmware-derived transaction sequence and later receive-probe report
are valuable leads, but they are not a published two-channel waveform/capture
that independently validates every status transition.

This is stronger evidence for the chip-level outbound electrical framing and
supports HOTD's `(status & 0x0c) == 0x0c` loop having the expected two-buffer
handshake shape.  It is still **not** a Model 2C/HOTD/837-12079 startup capture:
the report targets Model 2B host transport, does not record HOTD's response to
TX2=`0xff`, TX1=`0x01`, and does not establish reset latency or gun-board reply
bytes.  ArcadeRecomp therefore records these measured constraints but does not
turn them into an automatic ready status or synthetic RX data.

### Independent emulator convergence is a capture hypothesis, not proof

Two independently developed public emulators expose the same high-level gun
multiplexer model.  The pinned
[sm2-emu implementation](https://github.com/dmanlfc/sm2-emu/blob/7db71083ac3419b0c17af74bc6a1640365226238/src/hw/model2.cpp)
and [TGPulse implementation](https://github.com/deepblueworks/TGPulse/blob/7b8167577135e314080dc372dab2d2e7bdde1788/crates/tgpulse-core/src/memory.rs)
treat TX2 as a byte selector: indices 0..7 select low/high bytes of P1 Y,
P1 X, P2 Y and P2 X, while larger indices select an off-screen flag byte.
This agrees with a plausible interpretation of HOTD's repeated command/reply
shape and makes a useful discriminator for a future trace.

It is not independent hardware validation.  Both implementations synthesize
receive-ready status as constant `0x0c`; neither cites a CPU-correlated
837-12079 capture for the returned coordinates, flag polarity, reset response
or timing.  In particular, applying their rule to HOTD's initial TX2=`0xff`
would merely *predict* an off-screen/status reply.  ArcadeRecomp does not use
that prediction to pass startup.  A real capture can confirm or falsify the
selector ordering before any runtime model adopts it.

### Next discriminating evidence

Recover an attributable capture or circuit description for the exact 837-12079
and host revision. Establish direction and framing from the recorded signals,
then correlate the startup exchange with CPU-side status/RX accesses before
implementing responses. A Lost World trace would remain a cross-platform lead
until its equivalence to the original HOTD1 exchange is demonstrated. The new
sources do not close the authentic RX/status blocker or any completion gate.


## CPU-side serial transcript replay (opt-in, UNVERIFIED)

### Replay callback lifetime (2026-10-11)

The CPU-side replayer is uniquely owned but move-constructible. Its
315-5649 callbacks use weak references to the replay's private capture
session, not pointers to the replay object's address. Relocating the replay
between parsing and private native execution retains the exact cursor and
transaction checks. If the replay owner is destroyed, all subsequent
315-5649 status/RX/TX requests fail as unsupported device accesses; no
cached, stale, default or invented byte is returned. Copying a capture
session is explicitly disallowed.

These checks are validated with ROM-free GCC/Clang native tests. They do
not prove authentic receiver values or physical device timing.



`runtime/sega3155649_cpu_replay.hpp` implements a strict, bounded replay
backend for explicit *CPU-side* 315-5649 read/write observations.
`tools/hotd1_strict_boot_probe.cpp` can opt in using
`--serial-replay-unverified <PRIVATE trace file>`, a diagnostic research
mode intentionally separate from the strict default and `--serial-tx`.

The private trace file has the following text schema (entirely **invented
synthetic data**, not a captured HOTD1 cabinet or verified status):

```text
arcade-serial-cpu-replay-v1
count=4 dropped=0 complete=yes provenance=synthetic
1 W 0x01c00014 0xff
2 W 0x01c00012 0x01
3 R 0x01c0001a 0x00
4 R 0x01c0001a 0x0c
END
```

Format: strict contiguous 1-based ordinal; W or R; eight-digit hexadecimal
CPU byte-lane address; two-digit byte value. W rows are supported only at
documented TX1/TX2 ports; R rows only at STATUS/RX1/RX2. The source must
claim a bounded complete window and zero dropped observations, with
`provenance=synthetic` or `provenance=external_unverified`. The parser
rejects wrong addresses, reordered writes, missing reads, mismatching TX
values, malformed counts, nonzero dropped events, unspecified data,
unauthorized provenance claims and trailing records. At most 100,000
explicit rows are accepted. Replay consumption cannot advance when the
CPU transaction diverges: it stops under the existing device fault.

Example for a private, user-supplied trace:

```sh
strict_boot_probe /private/maincpu.bin 10000 \
  --serial-replay-unverified /private/cpu-side-3155649.txt
```

This mode **may supply status/RX bytes from the private input file**, so
any resulting native execution is a **controlled replay experiment** and
must **never** be called uninterrupted authentic original-arcade startup,
even if the supplied source labels itself external. The tool explicitly
prints `serial_replay_UNVERIFIED consumed/total/remaining`, and no input
trace is distributed. Missing bytes are never guessed; a completed replay
proves only conformance to the supplied CPU-access sequence, *not* chip
timing, physical TX completion, gun-board responses or cabinet provenance.
The default boot still stops at the unimplemented authentic RX/status
boundary. This is not a UART or gun hardware implementation.

The replay object must stay alive and stationary while attached to
`IO3155649`; it installs mutually exclusive legacy test/adapter callbacks
and is not compatible with the event-backed observed-buffer mode.

ROM-free tests (GCC/Clang UBSan and synthetic compiled probe):

```sh
python -m unittest discover -s tests -p test_sega_serial_cpu_replay.py -v
```
